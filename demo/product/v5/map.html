10Inbox and Decisions: approve, revert, audit

Things the mock exposed as missing from the plan

  • Per-row explanations for the client list ("why is this customer flagged") need a deterministic explainer in the engine; nothing in P1–P8 provides it.
  • Label arrival for monitoring: no defined path (upload, connector, or a labeling view).
  • Notifications and webhooks: L1 items and L3 actions need email/Slack/webhook; only the usage ledger exists.
  • Report agent is not a committed MVP dependency; start with a deterministic template and add generation only if it saves time without changing evidence.
  • Cleaning actions (dedupe, indicator for missingness): who owns them, agent proposal or a cleaning recipe?
  • Workspace-level decision records (policy changes) vs project records: one ledger or two?
  • Analyst role (run but not accept) is useful for teams; not in the current role model.
  • Session persistence for the lead agent: chat sessions, resumption, and reporting when the user leaves.

Things worth questioning

  • Does a small customer have a separate governance approver, or does the developer self-approve? If so, simplify approvals.
  • Manual hyperparameter overrides in the branch builder when the loop tunes.
  • Rule-proposer shadow runs in every improve iteration cost compute; limit to R2.
  • Daily windows, compute placement UI, Slack before webhooks: later.
  • Timeline layout and archived toggle in the graph.

Things that look right

  • One registry of tools for MCP, lead agent and forms keeps the surface small.
  • Rule answer beside every AI answer makes disagreements visible and cheap to audit.
  • The pipeline evidence view is the trust surface for both personas.
  • Inbox + Decisions + Governance separate "act now", "what happened" and "what is allowed".
  • Client view hides internals but keeps the trust figures and the undo.
