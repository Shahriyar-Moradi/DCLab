# Directory guide — Decision.ai / DCLab

This document walks the repository **folder by folder**. It is a map of the
codebase, not a product recap. For *what the product does*, see
`docs/PROJECT_RECAP.md`. For *who can see what*, see `ACCESS_MODEL.md` at the
repo root. For *how to click through the app*, see
`docs/HOW_TO_USE_THE_PLATFORM.md`.

**How to read this file:** each section is one directory. “What it is” is the
plain-language job of that folder. “What lives here” lists the important
files. Nested folders get their own subsections.

Generated artifacts (`artifacts/experiments/<uuid>/…`) are explained once, not
UUID-by-UUID — those folders are machine output, not source.

---

## 0. The repo at a glance

This is a **monorepo**: one Git repository that holds the Python API, the
Next.js website, YAML configs, sample data, trained-model files, benchmarks,
and docs.

```
decision_ai/
├── apps/            The two runnable products (API + website)
├── configs/         YAML: feature layers, policies, tasks, experiments
├── data/            Sample / synthetic / case-study / Olist tables
├── models/          Saved trained models (joblib), not source code
├── artifacts/       Experiment run output (generated; can be huge)
├── benchmarks/      Honesty harness: DCLab vs a single well-tuned model
├── scripts/         CI crawls, banned-term scan, Olist download
├── docs/            Human documentation (this file lives here)
├── reports/         Generated scorecards
├── .github/         GitHub Actions CI
├── Makefile         Local commands (db, migrate, test, run, web)
├── pyproject.toml   Python package + pytest config
├── alembic.ini      Database migration config (run from repo root)
├── ACCESS_MODEL.md  Living rule: clients never see raw ML
├── README.md        Project entry
└── docker-compose.yml / Dockerfile   Optional container path
```

Two logins, two URL trees:

| Who | Website | API |
|---|---|---|
| Client user | `/app/*` | `/app/*` |
| DCLab admin | `/admin/*` | `/admin/*` |

## 2. `.github/`

GitHub automation.

### `.github/workflows/`

- **`ci.yml`** — the only CI pipeline. On every push/PR it:
  1. Starts Postgres 16
  2. Installs the Python package, creates `decisionai` + `decisionai_test`, migrates
  3. Runs `pytest`
  4. Runs `python -m scripts.scan_banned_terms`
  5. Installs/builds the Next.js app (`tsc`, lint, `next build`)
  6. Seeds admin + client users
  7. Boots the real API + `next start`
  8. Runs `audit_admin_surface` (client / admin / anonymous) and `audit_client_surface`

If this folder is empty of other workflows, there are no separate deploy or
release pipelines yet.

## 3. `apps/`

The two applications that actually run.

```
apps/
├── api/     FastAPI backend (Python)
└── web/     Next.js 14 frontend (TypeScript)
```

They talk over HTTP. The website never imports Python. The API never imports
React. Shared *ideas* (a decision, an insight) are duplicated as Pydantic
models on the API and Zod schemas on the web.

---

The original “will this opportunity convert?” pipeline. Still used by

| File | Job |
|---|---|

| `predict.py` | Load that model and score a row |

| `generate_sample_csv.py` | Build a demo opportunities CSV |

This is **not** the full Lab search engine. That is `app/engine/`.

### 5.7 `apps/api/app/engine/` — DCLab experimentation engine

The automated data-science Lab. Admin-only. Tries many model × feature-group
combinations, drops leaks and weak copies, may blend survivors.

| Subfolder | Job |
|---|---|
| `types.py` (file) | Shared types: TaskSpec, SearchConfig, experiment status, … |
| `data/` | Loaders + data-quality checks |
| `datasets/` | Synthetic generator + Olist adapter |
| `schema/` | Profile a table (types, missingness, time columns) |
| `targets/` | Build the prediction target from a task spec |
| `features/` | Enumerate feature-group combinations |
| `leakage/` | Detect target leakage / future-looking columns |
| `validation/` | Time-aware train/validation/test splits |
| `models/` | Registry of model families the search may try |
| `search/` | Generate candidates + fingerprints (dedupe) |
| `evaluation/` | Metrics (PR-AUC, etc.) |
| `selection/` | Keep diverse, strong candidates |
| `ensemble/` | Blend members if the blend beats the best single |
| `experiments/` | Factory (build a run) + runner (execute) |
| `serving/` | Write member artifacts to disk |
| `reporting/` | Human-readable experiment report |

Admin UI `/admin/lab/*` and API `/admin/experiments*` call this via
`lab_service.py`.

### 5.8 `apps/api/app/sim/` — eight-question simulation harness

Same factory + policy, on synthetic “company” tables (Northstar, Shoppe, Atlas).

| File | Job |
|---|---|
| `catalog.py` | The eight use cases and paths to their layer/policy YAML |
| `generate.py` | Create synthetic CSVs under `data/sim/` |
| `predict.py` | Score entities |
| `decide.py` | Policy: pick an action given costs/uplifts/risk |
| `compare.py` | Naive vs best-single vs fusion vs oracle |
| `runner.py` / `run.py` | CLI: `python -m app.sim.run all` |

Admin simulations (`/admin/simulations`) and Client Labs (`/app/labs`) both
call `run_use_case`. Clients only see the translated slice.

### 5.9 `apps/api/app/cli/`

- **`main.py`** — `dclab` command. Includes `dclab user create --email --password --role`.

## 9. `configs/`

YAML the engines read. Changing these changes *behavior* without changing
Python, as long as the keys still match the code.

```
configs/
├── layers/           Which columns are features for a prediction task
│   ├── conversion_probability.yaml    M1 opportunity model
│   └── sim/                           One file per simulation use case
├── policies/         Actions, costs, uplifts, risk
│   ├── opportunity_prioritization.yaml   M1 decisions
│   ├── sim/                              Eight sim policies
│   └── case_studies/                     Benchmark case-study policies
├── tasks/            Lab task specs (purchase, revenue, next_purchase, …)
├── experiments/      Default Lab search config
└── case_studies/     Benchmark case-study task/layer specs
```

Client Labs and the simulation translator read action keys from
`configs/policies/sim/*.yaml`. A new action key must humanize cleanly or the
banned-term crawl will fail (see `offer_training`).

## 19. Mental model: request path through the folders

**Client generates a decision**

1. Browser: `apps/web/app/app/decisions/` → hook in `apps/web/lib/application/hooks.ts`
2. HTTP: `apps/web/lib/infrastructure/api-client.ts` → `POST /app/decisions/generate`
3. Route: `apps/api/app/api/decisions.py` (behind `client_api`)
4. Work: `generate_service.py` → `app/ml/predict.py` + policy YAML in `configs/policies/`
5. Translate: `app/translation/decisions.py`
6. Store: `app/db/models.py` Decision row
7. Return: `domain/decision.py` shape → Zod in `lib/domain/schemas.ts`

**Client runs a Lab trial**

1. `apps/web/app/app/labs/` → `POST /app/labs/runs`
2. `client_lab_service.py` → `app/sim/runner.py` (same engine as admin)
3. Translate: `app/translation/simulations.py`
4. Store: `client_lab_runs` (insights only) + `client_lab_run_audits` (raw, admin)

**Client drops any usual file on Labs (open ingest)**

1. `OpenFileCard` on `/app/labs` → `POST /app/labs/uploads`
2. `open_ingest.preview_upload` (no required columns) → `client_lab_upload_service`
3. Store: `client_lab_uploads` (file + fields noticed). No engine run.
4. Structuring messy files: `docs/LABS_DATA_UNDERSTANDING.md` (TODO)

**Admin runs an experiment**

1. `apps/web/app/admin/lab/experiments/`
2. `apps/api/app/api/lab.py` → `lab_service.py` → `app/engine/experiments/runner.py`
3. Writes `artifacts/experiments/<id>/` and DB experiment rows
4. Full metrics stay on `/admin`; never on `/app`
